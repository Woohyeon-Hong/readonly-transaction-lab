## 단순 조회에도 읽기 전용 트랜잭션이 필요할까?

## 목적

서비스 계층에서 단순 조회만 수행하는 메서드에 `@Transactional(readOnly = true)`를 적용할지 판단하기 위한 기준을 마련한다.

또한 읽기 전용 트랜잭션을 사용한다면, 단순히 습관적으로 적용하는 것이 아니라 어떤 근거로 사용하는지 설명할 수 있도록 한다.

### 비교 대상

서비스 계층에서 단순 조회를 수행할 때 선택할 수 있는 두 가지 방식을 비교한다. 비교 범위는 **성능 관점**으로 한정한다.

```java
@Transactional(readOnly = true)
public ReservationResponse findReservation(Long id) {
    ...
}
```

```java
public ReservationResponse findReservation(Long id) {
    ...
}
```

| 선택지 | 의미 |
| --- | --- |
| 읽기 전용 트랜잭션 사용 | 서비스 조회 메서드 전체를 `readOnly = true` 트랜잭션으로 감싼다 |
| 트랜잭션 없음 | 서비스 조회 메서드에 `@Transactional`을 사용하지 않는다 |

즉, 이 글에서는 일반 트랜잭션과 읽기 전용 트랜잭션을 비교하지 않는다.

오직 **읽기 전용 트랜잭션을 사용하는 경우**와**트랜잭션을 아예 사용하지 않는 경우**만 비교한다.

---

## **읽기 전용 트랜잭션의** 장점

### 1. 트랜잭션의 일관성은 유지하면서 비용을 줄일 가능성이 있다

이 글에서는 성능 관점에서 `read-only` 트랜잭션을 사용하는 경우와 **트랜잭션**을 사용하지 않는 경우를 비교한다. 하지만 성능만 보기 전에, **트랜잭션이 제공하는 장점**도 함께 고려해야 한다.

**단순 조회**라고 하더라도 하나의 응답을 만들기 위해 여러 `SELECT` 쿼리가 실행될 수 있다. 이때 트랜잭션을 사용하지 않으면 각 `SELECT`는 **독립적인 트랜잭션**으로 실행된다.

반면 `@Transactional`을 사용하면 여러 `SELECT` 쿼리를 **하나의 트랜잭션 범위**로 묶을 수 있다. 즉, **조회 메서드** 안에서 실행되는 여러 쿼리를 더 일관된 기준으로 처리할 수 있다.

문제는 이런 일관성을 얻기 위해 **트랜잭션** **비용**을 감수해야 한다는 점이다. 이때 **조회 전용 메서드**라면 `readOnly = true` 옵션을 사용할 수 있다.

`@Transactional(readOnly = true)`를 사용하면 **Spring**은 **트랜잭션**을 시작하면서 **JDBC** `Connection`에 읽기 전용 힌트를 전달할 수 있다.

```java
connection.setReadOnly(true);
```

이 힌트를 받은 **DB**나 **JDBC 드라이버**는 상황에 따라 **읽기 전용** **트랜잭션**으로 인식하고 일부 최적화를 적용할 수 있다.

가능한 성능상 이점은 다음과 같다.

- DB가 **읽기 전용 트랜잭션**으로 인식해 일부 최적화를 적용할 수 있다.
- **쓰기 작업**과 관련된 일부 비용을 줄일 가능성이 있다.
- `read-only connection`을 별도로 관리하는 구조에서 최적화 기준으로 사용할 수 있다.

다만 `readOnly = true`가 항상 성능 향상으로 이어지는 것은 아니다. 실제로 이 힌트를 어떻게 활용하는지는 DB, JDBC 드라이버, 커넥션 풀 설정에 따라 달라진다.

따라서 이 장점은 **“읽기 전용 트랜잭션이 트랜잭션 없음보다 항상 빠르다”**는 의미가 아니다. 핵심은 **트랜잭션**이 제공하는 일관된 조회 범위라는 장점은 유지하면서, 조회 전용 상황에서 발생하는 트랜잭션 비용을 줄일 가능성이 있다는 점이다.

#### 참고: 여러 SELECT를 하나의 트랜잭션으로 묶는다는 의미

>
>
>
> `@Transactional`을 사용하지 않으면 서비스 메서드 안에서 여러 `SELECT`가 실행되더라도, 각 `SELECT`는 **별도의 트랜잭션**으로 실행된다. 즉, 첫 번째 `SELECT`가 실행된 뒤 두 번째 `SELECT`가 실행되기 전까지 다른 트랜잭션이 **데이터를 변경하고 커밋**할 수 있다.
>
> 반면 `@Transactional`을 사용하면 서비스 메서드 안의 여러 `SELECT`를 **하나의 트랜잭션 범위**로 묶을 수 있다. 이 경우 여러 조회 쿼리가 같은 트랜잭션 안에서 실행되므로, **DB의 격리 수준**에 따라 더 일관된 기준으로 데이터를 조회할 수 있다.
>
> 예를 들어 `REPEATABLE READ`격리 수준에서는, 같은 트랜잭션 안의 일반 `SELECT`들이 같은 상태를 기준으로 **데이터를 조회**할 수 있다.
>
> 따라서 첫 번째 `SELECT` 이후 다른 트랜잭션이 **데이터를 변경하고 커밋**하더라도, 같은 트랜잭션 안에서 실행되는 이후 `SELECT`는 기존 상태를 기준으로 조회될 수 있다.
>
> 정리하면, 트랜잭션을 사용한다는 것은 단순히 쿼리를 실행하는 비용을 추가하는 것이 아니라, 여러 조회 쿼리를 하나의 일관된 조회 단위로 묶는다는 의미를 가진다.
>

### 2. 읽기/쓰기 DB 분리 구조에서 Replica 라우팅 기준으로 사용할 수 있다

**Primary DB**와 **Replica DB**를 분리한 구조에서는 `readOnly = true`가 라우팅 기준으로 사용될 수 있다.

예를 들어 다음과 같은 방식으로 요청을 분리할 수 있다.

- `@Transactional(readOnly = true)` → **Replica DB**로 라우팅
- `@Transactional` 또는 쓰기 트랜잭션 → **Primary DB**로 라우팅

이 경우 읽**기 전용 트랜잭션의 장점**은 단일 쿼리 자체가 더 빨라진다는 데 있지 않다. 핵심은 읽기 요청을 **Replica DB**로 분산하여 **Primary DB**의 부하를 줄일 수 있다는 점이다.

따라서 **읽기/쓰기 DB 분리 구조**를 사용한다면, 단순 조회라도 `readOnly = true`는 성능과 확장성 측면에서 의미를 가질 수 있다.

다만 이 장점은 별도의 라우팅 설정이 되어 있을 때만 적용된다. 단순히 `@Transactional(readOnly = true)`를 붙인다고 해서 **Spring**이 자동으로 **Replica DB**를 선택해주는 것은 아니다.

### 참고: DB Replication이란?

>
>
>
> **DB Replication**은 두 개 이상의 **DBMS**를 사용해 데이터를 복제하고, **DB 부하를 분산**하는 구조입니다.
>
> 일반적으로 하나의 **Primary DB**와 하나 이상의 **Replica DB**로 구성합니다. **Primary DB**는 **데이터 변경 작업**을 담당하고, **Replica DB**는 Primary DB의 데이터를 복제한 뒤 주로 **조회 작업**을 담당합니다.
>
> 이를 통해 다음과 같은 효과를 얻을 수 있습니다.
>
> - **조회 요청**을 **Replica DB**로 분산하여 **Primary DB**의 부하를 줄일 수 있다.
> - **Primary DB** 장애 시 **Replica DB**를 활용해 **가용성**을 높일 수 있다.
> - 데이터를 복제해두기 때문에 백업과 안정성 측면에서도 이점이 있다.
> - 읽기 요청이 많은 서비스에서 **수평 확장**에 유리하다.
>
> **Replication**에서 자주 사용하는 구조는 아래와 같습니다.
>
> - **Primary DB**: `INSERT`, `UPDATE`, `DELETE` 같은 쓰기 작업을 처리한다.
> - **Replica DB**: Primary DB의 데이터를 복제하고, 주로 `SELECT` 같은 읽기 작업을 처리한다.

### 3. JPA 사용 시 영속성 컨텍스트 관련 최적화 여지가 있다

`JPA`를 사용하는 경우, 읽기 전용 트랜잭션은 `Hibernate` 같은 ****`JPA` **구현체**에 **읽기 전용 힌트**를 전달할 수 있다.

이 경우 상황에 따라 다음과 같은 최적화 여지가 생길 수 있다.

- **변경 감지**를 위한 **스냅샷 관리 비용** 감소 가능
- `flush` 관련 비용 감소 가능
- 대량 엔티티 조회 시 **영속성 컨텍스트** 관리 비용 감소 가능

다만 이 장점은`JPA`를 사용할 때의 이야기다. `JdbcTemplate`, `MyBatis`, 순수 **JDBC**를 사용하는 경우에는 `dirty checking`이나 `flush` 자체가 없기 때문에 해당하지 않는다.

또한 `JPA`를 사용하더라도 **OSIV 설정,**  **DTO projection** 사용 여부, 조회 데이터 규모에 따라 실제 이점은 달라진다.

### 참고: `dirty checking`과 `flush`란 무엇이고, 어떻게 최적화할 수 있는가?

>
>
>
> `JPA`는 엔티티를 조회하면 이를 **영속성 컨텍스트**에 저장한다. **영속성 컨텍스트**는 같은 트랜잭션 안에서 엔티티를 캐시하는 역할을 하며, 동시에 엔티티의 변경 여부를 추적하는 역할도 수행한다.
>
> `JPA`는 엔티티가 처음 조회되었을 때의 상태를 **스냅샷**으로 저장해둔다. 그리고 트랜잭션이 끝나는 시점에 현재 엔티티 상태와 스냅샷을 비교하여 변경 여부를 판단한다. 이처럼 엔티티의 변경을 감지하는 과정을 `dirty checking`이라고 한다.
>
> 변경이 감지되면 JPA는 해당 변경 내용을 SQL로 만들어 DB에 반영한다. 이때 **영속성 컨텍스트**의 변경 내용을 DB에 동기화하는 과정을 `flush`라고 한다.
>
> 그런데 단순 조회에서는 엔티티를 변경하지 않는다. 따라서 엔티티 변경을 감지하기 위한 스냅샷 관리나 flush 준비 과정이 불필요한 비용이 될 수 있다.
>
> 이때 `@Transactional(readOnly = true)`를 사용하면 **Spring**과 **JPA 구현체**는 조회 전용 트랜잭션이라는 힌트를 활용할 수 있다. 예를 들어 **Hibernate**는 **flush 모드**를 조정하거나, 읽기 전용으로 조회된 엔티티에 대해 변경 감지에 필요한 관리 비용을 줄일 수 있다.
>
> 즉, `JPA` 환경에서 읽기 전용 트랜잭션은 단순히 **JDBC Connection**에 `read-only`힌트를 전달하는 것뿐만 아니라, **영속성 컨텍스트**의 변경 감지와 `flush` 관련 비용을 줄일 수 있는 최적화 여지를 제공한다.
>

### 참고:  **OSIV 설정,**  **DTO projection** 사용 여부에 따라 왜 달라질 수 있는가?

>
>
>
> JPA에서 읽기 전용 트랜잭션의 성능 개선 효과는 **OSIV 설정**과 **DTO projection 사용 여부**에 따라 달라질 수 있다.
>
> 먼저 **OSIV(Open Session In View)**는 영속성 컨텍스트를 어디까지 유지할지 결정하는 설정이다. OSIV가 꺼져 있으면 영속성 컨텍스트는 보통 트랜잭션 범위까지만 유지된다. 따라서 `@Transactional(readOnly = true)`를 사용한 경우, 조회한 엔티티는 서비스 계층의 트랜잭션 안에서만 관리되고, 읽기 전용 트랜잭션의 최적화 효과도 이 범위 안에서 적용된다.
>
> 반면 OSIV가 켜져 있으면 트랜잭션이 끝난 뒤에도 HTTP 응답이 완료될 때까지 영속성 컨텍스트가 유지될 수 있다. 이 경우 트랜잭션 밖에서도 지연 로딩이 발생하거나 엔티티 관리 비용이 이어질 수 있다. 따라서 동일하게 읽기 전용 트랜잭션을 적용했더라도, OSIV 설정에 따라 영속성 컨텍스트의 유지 범위와 지연 로딩 가능성이 달라지고, 그에 따라 실제 성능 특성도 달라질 수 있다.
>
> DTO projection 사용 여부도 중요하다. DTO projection은 필요한 컬럼을 직접 조회해 **DTO**로 바로 매핑하는 방식이다. 이 경우 조회 결과를 엔티티로 관리하지 않기 때문에, 영속성 컨텍스트의 스냅샷 관리, `dirty checking,` `flush` 관련 최적화 효과가 거의 없다.
>
> 즉, 읽기 전용 트랜잭션의 성능 개선 효과는 엔티티를 영속성 컨텍스트에서 관리하는 상황에서 더 의미가 있고, DTO projection처럼 엔티티 관리 자체를 피하는 조회 방식에서는 상대적으로 제한적이다.
>

## **읽기 전용 트랜잭션의** 단점

### 1. 트랜잭션 시작/종료 비용이 발생한다

`readOnly = true`라고 해도 트랜잭션을 사용한다는 사실은 변하지 않는다.

따라서 트랜잭션을 사용하지 않는 조회에 비해 다음과 같은 **부가 비용**이 발생할 수 있다.

- **트랜잭션** **인터셉터** 실행
- **트랜잭션** 시작
- **트랜잭션** 종료
- `commit` 또는 `rollback` 처리
- `Connection` 상태 변경
- `readOnly` 설정 전달
- **트랜잭션 동기화 자원** 관리

즉, `readOnly = true`는 **트랜잭션 비용**을 완전히 없애는 옵션이 아니다.

트랜잭션은 그대로 사용하되, 조회 전용이라는 힌트를 통해 일부 비용을 줄일 가능성을 제공하는 옵션에 가깝다.

따라서 단순 단건 조회처럼 `SQL` 하나만 실행하고 바로 응답을 반환하는 경우에는, **트랜잭션 시작/종료 비용**이 `readOnly` 힌트로 얻는 이점보다 클 수 있다.

특히 `JPA`를 사용하지 않는 `JdbcTemplate`, `MyBatis`와 같은 순수 **JDBC** 환경에서는 `dirty checking`이나 `flush` 비용 자체가 없기 때문에, `readOnly = true`로 얻을 수 있는 최적화 효과가 더 제한적일 수 있다.

### 2. 서비스 메서드 동안 리소스를 더 오래 유지할 수 있다

**읽기 전용 트랜잭션**을 사용하면 **트랜잭션 범위**가 **서비스 메서드 전체**로 확장된다. 즉, `Repository`나 `DAO` 호출이 끝났더라도 서비스 메서드가 종료되기 전까지 트랜잭션 관련 리소스가 유지될 수 있다.

이 과정에서 다음과 같은 비용이 발생할 수 있다.

- **커넥션** 점유 시간 증가
- **트랜잭션 동기화 자원** 유지
- **트랜잭션 컨텍스트** 관리 비용
- `JPA` 사용 시 **영속성 컨텍스트** 유지 비용
- `JPA` 사용 시 조회 엔티티 관리 비용

물론 여러 조회 쿼리를 **하나의 일관된 트랜잭션 범위**로 묶어야 한다면 이러한 비용은 감수할 만하다.

하지만 `Repository`나 `DAO` 한 번 호출로 필요한 데이터를 모두 조회하고 바로 반환하는 **단순 조회**라면, 서비스 메서드 전체를 트랜잭션으로 감싸는 것이 오히려 불필요한 리소스 유지 비용을 만들 수 있다.

따라서 읽기 전용 트랜잭션은 “조회니까 항상 붙이는 설정”이라기보다는, 조회 과정에서 트랜잭션 범위가 실제로 필요한지 함께 고려해서 적용하는 것이 적절하다.

## 실험해보기

### 실험에 들어가며

앞서 정리한 읽기 전용 트랜잭션의 장단점은 일반적인 관점에서의 이야기다. 실제로 `@Transactional(readOnly = true)`가 성능상 유리한지는 실행 환경과 조회 방식에 따라 달라질 수 있다.

예를 들어 같은 단순 조회라도 다음 조건에 따라 결과가 달라질 수 있다.

- JPA를 사용하는가?
- JdbcTemplate이나 MyBatis처럼 JPA를 사용하지 않는가?
- JPA를 사용한다면 OSIV가 켜져 있는가?
- OSIV가 꺼져 있는가?
- DTO projection으로 바로 조회하는가?
- 엔티티를 조회한 뒤 연관 객체에 접근하는가?
- 읽기/쓰기 DB 분리 구조가 있는가?

따라서 지금부터는 몇 가지 조회 시나리오를 정해두고, 각 상황에서 **읽기 전용 트랜잭션을 사용하는 경우**와 **트랜잭션을 사용하지 않는 경우**를 비교해본다.

실험의 목표는 각 상황에서 두 방식 중 어느 쪽이 성능적으로 더 유리한지 확인하는 것으로 한다.

### 측정 기준

이번 실험에서는 **서비스 조회 메서드 전체 실행 시간**을 기준으로 성능을 측정한다.

측정 범위는 서비스 메서드가 호출된 시점부터 **응답 DTO**가 생성되어 반환되기 직전까지다.

#### 포함되는 비용

- 트랜잭션 시작/종료 비용
- `Repository/DAO` 호출 비용
- DB 조회 비용
- `Entity` 생성 및 매핑 비용
- 응답 DTO 변환 비용
- **JPA** 사용 시 영속성 컨텍스트 관련 비용
- **JPA** 사용 시 지연 로딩으로 인한 추가 조회 비용

서비스 계층의 조회 메서드는 일반적으로 엔티티를 그대로 반환하지 않고 응답 DTO로 변환해 반환한다. 따라서 DTO 변환은 조회 유스케이스의 일부로 보고 측정 범위에 포함한다.

특히 **JPA** 환경에서 `OSIV`를 끈 경우에는 트랜잭션 경계 안에서 DTO 변환을 수행하는지 여부가 지연 로딩 가능 여부에 영향을 줄 수 있다. 따라서 DTO 변환 시간을 제외하지 않는다.

#### 수집할 측정값

각 실험에서는 단일 실행 시간이 아니라 반복 실행 결과를 수집한다.

- 평균
- 중간값
- 최소값
- 최대값
- p95

평균만으로 판단하지 않는다. 일부 실행 시간이 튀면 평균이 왜곡될 수 있기 때문이다. 따라서 중간값과 p95를 함께 확인한다.

#### 결과 해석 기준

결과는 단순히 한 번 더 빠른지를 기준으로 판단하지 않는다.

- 반복 측정에서 일관된 차이가 나타나는가?
- 평균뿐 아니라 중간값과 p95에서도 비슷한 경향이 나타나는가?
- 차이가 측정 오차나 실행 환경의 흔들림보다 충분히 큰가?
- 단건 조회와 대량 조회에서 경향이 다르게 나타나는가?

차이가 작거나 실행마다 방향이 바뀐다면, 성능상 유의미한 근거로 보기 어렵다.

반대로 평균, 중간값, p95에서 일관된 차이가 반복적으로 나타난다면, 해당 환경에서는 `@Transactional(readOnly = true)` 적용 여부가 성능에 영향을 준다고 볼 수 있다.

### 고정할 조건과 그 이유

이번 실험에서는 `@Transactional(readOnly = true)` 적용 여부에 따른 성능 차이를 확인하기 위해, 그 외의 조건은 최대한 동일하게 유지한다.

#### 1. 데이터베이스와 JDBC Driver

`@Transactional(readOnly = true)`는 JDBC `Connection`에 read-only 힌트를 전달할 수 있다.

하지만 이 힌트를 실제로 어떻게 처리하는지는 DB와 JDBC Driver에 따라 달라질 수 있다. 따라서 DB와 JDBC Driver 버전을 명시해야 실험 결과를 해석하기 쉽다.

- DB: MySQL 8.0.x
- JDBC Driver: MySQL Connector/J 8.0.x
- Schema: reservation, time 테이블
- Index: 기본 PK/FK 인덱스 외 추가 인덱스 없음
- Initial Data: 단건 조회용 데이터 1건, 대량 조회용 데이터 50,000건

#### 2. 애플리케이션 실행 환경

Java, Spring, JVM 옵션, 로깅 설정에 따라 실행 시간이 달라질 수 있다. 특히 SQL 로그가 켜져 있으면 측정 결과가 왜곡될 수 있으므로 비활성화한다.

- Java: 17
- Spring Boot: 3.x.x
- Spring Framework: 6.x.x
- Profile: test
- JVM Options: 별도 옵션 없음
- SQL Logging: off

#### 3. 커넥션 풀 설정

커넥션 획득 시간과 커넥션 상태 초기화 비용은 서비스 메서드 실행 시간에 영향을 줄 수 있다. 또한 읽기 전용 트랜잭션은 커넥션의 read-only 상태 설정 및 복구 과정과 관련될 수 있으므로 커넥션 풀 설정을 고정한다.

- Connection Pool: HikariCP
- maximumPoolSize: 10
- minimumIdle: 10
- connectionTimeout: 30000ms
- idleTimeout: 600000ms
- maxLifetime: 1800000ms

#### 4. 데이터 양과 데이터 상태

데이터 양과 데이터 형태는 DB 조회 시간, 객체 생성 시간, DTO 변환 시간에 영향을 준다. 따라서 같은 시나리오 안에서는 동일한 데이터 상태를 유지한다.

또한 실험 중 데이터가 변경되면 조회 결과와 실행 시간이 달라질 수 있으므로, 실험 중에는 조회 외의 쓰기 작업을 수행하지 않는다.

- Single Read: id = 1 데이터 1건 조회
- Bulk Read: reservation 50,000건 조회
- Related Data: reservation 1건당 time 1건 참조
- Data Change During Test: 없음

#### 5. 서비스 테스트 트랜젝션

서비스 테스트 메서드에는 `@Transactional`을 붙이지 않는다.

- 테스트 트랜잭션이 서비스 트랜잭션 비교를 오염시킬 수 있다.
- `@Transactional` 없는 서비스 메서드도 테스트 트랜잭션 안에서 실행될 수 있다.
- readOnly 있음/없음 비교가 정확하지 않아진다.

대신:

- given 데이터 삽입은 측정 구간 밖에서 수행한다.
- 테스트 전후 데이터 초기화는 직접 DELETE/TRUNCATE로 처리한다.

#### 6. 워밍업

첫 실행에는 클래스 로딩, JIT 컴파일, 커넥션 초기화, DB 캐시 상태 등의 영향이 섞일 수 있다. 이 영향이 특정 비교 대상에만 몰리면 측정 결과가 왜곡될 수 있으므로, 실제 측정 전에 워밍업 실행을 수행한다.

- Warm-up Count: 100회
- Warm-up Result: 최종 측정값에서 제외
- Warm-up Order: readOnly 있음 / 없음 교차 실행

#### 7. 측정 방식

측정 방식이 달라지면 결과를 비교하기 어렵다.

워밍업 없이 측정하면 클래스 로딩, JIT 컴파일, 커넥션 초기화, DB 캐시 상태의 영향이 섞일 수 있다. 또한 한쪽을 먼저 몰아서 실행하면 측정 순서에 따른 캐시 영향이 생길 수 있으므로 교차 실행한다.

- Measurement: `System.nanoTime()` 기반 반복 측정
- Warm-up: 100회
- Measurement Count: 1,000회
- Execution Order: readOnly 있음/없음 교차 실행
- Aggregation: 평균, 중간값, 최소값, 최대값, p95

> ### 1. JdbcTemplate + 트랜잭션 없음
>
> | argument | count |
> | --- | --- |
> | select * FROM reservation_time WHERE id = 1 | 1000 |
>
> 트랜잭션을 명시적으로 사용하지 않은 경우에는 조회 쿼리만 1,000회 실행되었다.
>
> 즉, 애플리케이션에서 수행한 SELECT 외에 별도의 트랜잭션 관련 명령은 관찰되지 않았다.
>
> ### 2. JdbcTemplate + readOnly 트랜잭션
>
> | argument | count |
> | --- | --- |
> | SET SESSION TRANSACTION READ ONLY | 1000 |
> | SET autocommit=0 | 1000 |
> | select * FROM reservation_time WHERE id = 1 | 1000 |
> | COMMIT | 1000 |
> | SET autocommit=1 | 1000 |
> | SET SESSION TRANSACTION READ WRITE | 1000 |
>
> `@Transactional(readOnly = true)`를 사용한 경우에는 SELECT 쿼리 외에도 트랜잭션 시작과 종료, 그리고 read-only 설정과 복구를 위한 명령이 함께 전달되었다.
>
> 즉, 읽기 전용 트랜잭션이라고 해도 트랜잭션 자체가 사라지는 것은 아니다.
>
> Spring은 트랜잭션을 시작하기 위해 `autocommit`을 끄고, DB 세션을 읽기 전용으로 설정한 뒤, 조회가 끝나면 `COMMIT`, `autocommit` 복구, `READ WRITE` 복구 작업을 수행한다.
>
> ### 3. JPA + readOnly 트랜잭션
>
> | argument | count |
> | --- | --- |
> | SET SESSION TRANSACTION READ ONLY | 1000 |
> | SET autocommit=0 | 1000 |
> | select te1_0.id,te1_0.start_at from reservation_time te1_0 where te1_0.id=1 | 1000 |
> | COMMIT | 1000 |
> | SET autocommit=1 | 1000 |
> | SET SESSION TRANSACTION READ WRITE | 1000 |
>
> JPA를 사용하는 경우에도 readOnly 트랜잭션에서 전달되는 트랜잭션 관련 명령은 JdbcTemplate과 동일하게 나타났다.
>
> 차이는 조회 SQL의 형태다.
>
> JdbcTemplate은 직접 작성한 SQL이 그대로 실행되지만, JPA는 Hibernate가 엔티티 매핑 정보를 바탕으로 SQL을 생성한다.
>
> ### 결과 해석
>
> 이번 보조 실험을 통해 `@Transactional(readOnly = true)`를 사용하면 단순 SELECT만 실행되는 것이 아니라, DB에 다음과 같은 부가 명령이 함께 전달될 수 있음을 확인했다.
>
> - `SET SESSION TRANSACTION READ ONLY`
> - `SET autocommit=0`
> - `COMMIT`
> - `SET autocommit=1`
> - `SET SESSION TRANSACTION READ WRITE`
>
> 따라서 `readOnly = true`는 트랜잭션 비용을 없애는 설정이 아니다.
>
> 오히려 트랜잭션을 실제로 시작하고 종료하기 때문에, 트랜잭션을 사용하지 않는 조회에 비해 추가 명령이 발생할 수 있다.
>
> 다만 이 결과만으로 `readOnly` 트랜잭션이 항상 불리하다고 볼 수는 없다.
>
> 읽기 전용 트랜잭션은 여러 조회 쿼리를 하나의 일관된 트랜잭션 범위로 묶을 수 있고, DB나 JDBC Driver, JPA 구현체가 read-only 힌트를 활용해 일부 최적화를 적용할 가능성도 있다.
>
> 즉, 이번 보조 실험의 의미는 다음과 같다.
>
> `@Transactional(readOnly = true)`는 조회 전용이라는 의도를 전달하고 최적화 가능성을 제공하지만, 트랜잭션 자체의 시작/종료 비용은 여전히 존재한다. 따라서 단순 단건 조회처럼 SELECT 하나만 실행하는 경우에는 이러한 부가 명령의 비용이 상대적으로 크게 드러날 수 있다.
>
